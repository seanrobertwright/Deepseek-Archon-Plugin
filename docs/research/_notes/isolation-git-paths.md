## 1. Isolation engine (`packages/isolation/src`) — most detail

### 1.1 IsolationRequest discriminated union

Branded `RepoPath`/`BranchName` come from `@archon/git` (types.ts:9). Base interface `IsolationRequestBase` (types.ts:32-89):
- `codebaseId: string` (DB codebase id; types.ts:34)
- `codebaseName?: string` — "owner/repo" format; resolves the project-scoped worktree path even when a local repo's path isn't under `workspacesPath` (types.ts:37-41)
- `canonicalRepoPath: RepoPath` — "the real path with symlinks resolved and `~` expanded"; normally the primary checkout; a `--separate-git-dir` linked checkout is a valid anchor (types.ts:44-56)
- `baseBranch?: BranchName` — preferred base for new worktrees; populated from the codebase's stored `default_branch`; `worktree.baseBranch` still wins (types.ts:59-66)
- `baseOverride?: BranchName` — per-dispatch `--base` flag; highest precedence in base resolution (types.ts:69-77)
- `description?: string` (types.ts:79)
- `gitIdentity?: { email: string; name?: string }` — stamps new worktrees with the originating user's GitHub no-reply identity (types.ts:82-88)

Request variants (types.ts:91-135):
- `IssueIsolationRequest` `{ workflowType: 'issue'; identifier: string }` (91-94)
- `PRIsolationRequest` `{ workflowType: 'pr'; identifier: string; prBranch: BranchName; prSha?: string; isForkPR: boolean }` — "The actual branch name of the PR (required for PR workflows)" (96-105)
- `ReviewIsolationRequest` `{ workflowType: 'review'; identifier: string }` (107-110)
- `ThreadIsolationRequest` `{ workflowType: 'thread'; identifier: string }` — "Thread ID (will be hashed for branch name)" (112-116)
- `TaskBranchSelection` = `{ kind: 'new'; branch?; fromBranch? } | { kind: 'existing'; branch }` (118-120) and `TaskIsolationRequest` `{ workflowType: 'task'; identifier: string; taskBranch?: TaskBranchSelection }` — "creates a branch or continues an exact existing branch" (122-128)
- Union `IsolationRequest` (130-135). Type guard `isPRIsolationRequest` (240-242).

### 1.2 IsolationHints and result/status types

`IsolationHints` (types.ts:246-269): `workflowType?`, `workflowId?`, PR-specific `prBranch?/prSha?/isForkPR?/prFetchFailed?`, task `taskBranch?` ("Only consumed when workflowType === 'task'"), `baseBranch?` ("reused worktrees are validated with merge-base"), `linkedIssues?: number[]`, `linkedPRs?: number[]`, `suggestedBranch?`.

`IsolationBlockReason = 'creation_failed'` (types.ts:271) — the **only** block reason.

`ResolutionMethod` (types.ts:400-405):
```
| { type: 'existing' }
| { type: 'workflow_reuse' }
| { type: 'linked_issue_reuse'; issueNumber: number }
| { type: 'branch_adoption'; branch: string }
| { type: 'created'; autoCleanedCount?: number }
```

`IsolationResolution` verbatim (types.ts:407-417):
```
| { status: 'resolved'; env: IsolationEnvironmentRow; cwd: string;
    method: ResolutionMethod; warnings?: string[] }
| { status: 'stale_cleaned'; previousEnvId: string }
| { status: 'none'; cwd: string }
| { status: 'blocked'; reason: IsolationBlockReason; userMessage: string }
```
(There is no 'pending'/other status — exactly these four.)

### 1.3 Resolver decision steps, in order (`resolver.ts`)

Class docstring states resolution order 1-6 with no limit step (resolver.ts:60-70). `resolve(request: ResolveRequest)` (resolver.ts:91-231):

1. **Existing environment reference** — `request.existingEnvId` (94-100). `checkExisting()` (268-289): `store.getById(envId)`; if the row exists **and** `worktreeExists(toWorktreePath(env.working_path))` → `{ status:'resolved', method:{type:'existing'} }`, plus optional warnings from `collectBaseBranchWarnings` when `hints.baseBranch` is set (238-263: runs `isAncestorOf(toWorktreePath(env.working_path), 'origin/${baseBranch}')`; mismatch emits warning `Worktree branch '<x>' is not based on '<y>'. Recreate with: archon complete <branch> --force` at 251-254). If the row exists but the worktree is gone → `markDestroyedBestEffort` (store `updateStatus 'destroyed'`, never throws; 455-465) and returns null → caller returns **`{ status:'stale_cleaned', previousEnvId }`** (99).
2. **No codebase = no isolation** — `if (!request.codebase) return { status: 'none', cwd: '/workspace' }` (102-105). (`'/workspace'` is the docker/legacy sentinel.)
3. **Folder-kind short-circuit** (2b; 121-131): when `request.codebase.kind === 'folder'`, calls `resolveFolderBackend(folderCodebase, { container: false })` then `backend.prepare(...)` and returns `{ status:'none', cwd: prepared.cwd }`. The in-place backend returns the real folder path. The comment at 113-120 states `prepared.execContext` is **intentionally dropped** in Phase A (the 'none' variant carries no execContext channel) — only the CLI path carries container execContext.
4. **Canonical repo path resolution** (145-180): `getCanonicalRepoPath(codebase.defaultCwd)`; `CanonicalRepoPathUnavailableError` (linked worktree from external `--separate-git-dir`) → falls back to `toRepoPath(codebase.defaultCwd)` (153-154). Other errors that `isKnownIsolationError` → **`blocked`** with `classifyIsolationError(err)` + `' Execution blocked to prevent changes to shared codebase. Please resolve the issue and try again.'` (171-178); unknown errors re-throw (crash, not silent block).
5. **Workflow reuse** — `findReusable(codebase.id, canonicalPath, workflowType, workflowId, baseBranch)` (182-198; 325-354): `store.findActiveByWorkflow(codebaseId, workflowType, workflowId)`; verifies on-disk worktree exists and **ownership** via `assertWorktreeOwnership` → `verifyWorktreeOwnership` (300-315; cross-clone mismatch **throws**, preserving the other clone's row); returns `{ status:'resolved', method:{type:'workflow_reuse'} }` + warnings. Default `workflowType = hints?.workflowType ?? 'thread'` and `workflowId = hints?.workflowId ?? ''` (135-136).
6. **Linked issue sharing** (200-204; `findLinkedIssueEnv` 366-400): if `hints?.linkedIssues?.length`, iterates issues, `store.findActiveByWorkflow(codebaseId, 'issue', String(issueNum))`; ownership-verified → `{ status:'resolved', method:{ type:'linked_issue_reuse', issueNumber } }`. Cross-clone mismatch throws and stops iteration (comment 356-365).
7. **PR branch adoption** (206-218; `tryBranchAdoption` 409-449): only if `hints?.prBranch`; `findWorktreeByBranch(canonicalRepoPath, prBranch)`; ownership-verified → **creates a DB row** via `store.create` with `metadata: { adopted: true, adopted_from: 'skill' }` (431-440) → `{ status:'resolved', method:{ type:'branch_adoption', branch: prBranch } }`.
8. **Create new** — `createNewEnvironment(...)` (220-230; 470-607). Builds the per-type request: for `'pr'`, `prBranch: hints?.prBranch ?? toBranchName('pr-<workflowId>')`, `prSha`, `isForkPR: hints?.isForkPR ?? false` (491-498); for `'task'` threads `taskBranch` (499-504); else `workflowType` only (506-510). Calls `provider.create(...)`; known errors → `blocked` (524-541), unknown → rethrow. On success calls `store.create` with `metadata: { related_issues: hints?.linkedIssues ?? [], related_prs: hints?.linkedPRs ?? [] }` (548-560); if `store.create` fails it best-effort **destroys the orphaned worktree** (573-595: `provider.destroy(workingPath, { canonicalRepoPath, branchName, force: true })`) and rethrows. Returns `{ status:'resolved', method:{ type:'created' } }` (+ provider warnings) (600-606).

**makeRoom / limit-check pointer**: NOT in the resolver. `IsolationResolverDeps.cleanup` is declared `{ makeRoom: (codebaseId, repoPath) => Promise<{ removedCount: number }>; getBreakdown: (codebaseId, repoPath) => Promise<WorktreeStatusBreakdown> }` (resolver.ts:48-56; also types.ts:52-53 / WorktreeStatusBreakdown types.ts:342-350). grep confirms `deps.cleanup` is never dereferenced in resolver.ts (constructor only reads `store`, `provider`, `staleThresholdDays` — resolver.ts:77-79). Default `staleThresholdDays = 14` (`DEFAULT_STALE_THRESHOLD_DAYS`, resolver.ts:58); the constructor throws on non-positive values (81-86). The caller-side wiring lives in core (`packages/core/src/orchestrator/orchestrator.ts:110-121` builds `new IsolationResolver({ store, provider, cleanup: { makeRoom: ...cleanupToMakeRoom..., getBreakdown: getWorktreeStatusBreakdown }, staleThresholdDays })`) — outside this scope, but that is where capacity eviction happens.

### 1.4 Provider interface and WorktreeProvider internals

`IsolationProviderType = 'worktree' | 'container' | 'vm' | 'remote'` (types.ts:24); `EnvironmentStatus = 'active' | 'destroyed'` (28). `IIsolationProvider` (217-236): `providerType`, `create(request): Promise<IsolatedEnvironment>`, `destroy(envId, options?): Promise<DestroyResult>` ("Best-effort cleanup. Throws only for unexpected errors"), `get(envId)`, `list(codebaseId)` ("codebaseId is the canonical repo path"), optional `adopt?(path)`, `healthCheck(envId)`. `DestroyResult` = `{ worktreeRemoved, branchDeleted: boolean|null, remoteBranchDeleted: boolean|null, directoryClean, warnings }` (194-202). `IsolatedEnvironment = WorktreeEnvironment` only (166-172: `provider:'worktree', branchName, metadata: WorktreeMetadata` where metadata is `{adopted:true, adoptedFrom?:'path'|'branch', request?}` | `{adopted:false, request?}` — 139-150). envId for worktrees **is the filesystem path** (docstring at 152-154, worktree.ts:174-178).

**WorktreeProvider** (`providers/worktree.ts`, `providerType = 'worktree'` line 149):
- `create` (162-203): loads repo config exactly once via `loadConfig(canonicalRepoPath)` (fail-loud, 163-170); computes branch + path; **envId = worktreePath**; adoption path first (`findExisting`, 649-734), else `createWorktree` (761-835). Metadata: for `taskBranch.kind === 'existing'` sets `{ adopted: true, adoptedFrom: 'branch', request }`, else `{ adopted: false, request }` (189-200).
- **Branch naming** `generateBranchName` (594-618): `issue` → `` `archon/issue-${identifier}` ``; `pr` non-fork → **`request.prBranch` verbatim** (real remote branch, pushes to the PR); fork → `` `archon/pr-${identifier}-review` ``; `review` → `` `archon/review-${identifier}` ``; `thread` → `` `archon/thread-${this.shortHash(identifier)}` ``; `task` `existing` → `taskBranch.branch`, `task` `new`+branch → `taskBranch.branch`, else `` `archon/task-${this.slugify(identifier)}` ``. `shortHash` = `sha256(...)` hex truncated to **8 chars** (1453-1456). `slugify` = lowercase, `[^a-z0-9]+`→`-`, strip edge dashes, **max 50 chars** (1461-1467).
- **Path layout** `getWorktreePath` (634-644): `getWorktreeBase(canonicalRepoPath, codebaseName, { repoLocal })` then `join(base, branchName)`. `repoLocal` override validated by `resolveRepoLocalOverride` (104-146: relative only, no `..`, must not escape repo root — absolute throws "worktree.path must be relative…" 112-117). Config `path` sourced from `.archon/config.yaml > worktree.path` (types.ts:302-314). Two layouts (git/src/worktree.ts:110-123): `repo-local` → `<repoRoot>/<config.path>/<branch>`; `workspace-scoped` → `~/.archon/workspaces/<owner>/<repo>/worktrees/<branch>` via `getProjectWorktreesPath(owner, repo)`.
- **Adoption detection** `findExisting` (649-734): (a) if path exists → verify `verifyWorktreeOwnership` (cross-clone throws; 667-680), and for exact task branch verify `getCurrentBranchStrict` matches (682-690); (b) else if `prBranch`/exact task branch → search `git worktree list` / `findWorktreeByBranch` for an externally-created checkout, with the same ownership guard (696-731). Returns env built by `buildAdoptedEnvironment` (736-751).
- **Sync before create** `syncWorkspaceBeforeCreate` (929-977): base precedence `request.baseOverride ?? worktreeConfig?.baseBranch ?? request.baseBranch` then auto-detect (788-794); `syncWorkspace` mode `'reset'` only when the path is an Archon-managed clone under `getArchonWorkspacesPath()`, else `'fast-forward'` (941-948).
- **PR creation** `createFromPR` (1063-1089): same-repo PR → `git -C <repo> worktree add <path> -b <prBranch> <remote>/<prBranch>` after a `syncWorkspace mode:'fetch-only'` (1105-1127), fallback `worktree add <path> <prBranch>` on "already exists" (1131-1134), then `branch --set-upstream-to <remote>/<prBranch>` (1142-1146). Fork PR `createFromForkPR` (1160-1221): with `prSha`, `git fetch <remote> pull/<n>/head` (no ref lock) then `worktree add <path> <prSha>` then `checkout -b <reviewBranch> <prSha>`; without SHA, fetch into local `refs/heads/<reviewBranch>` (`pull/<n>/head:<reviewBranch>`, `fetchWithRefLockRetry`) then `worktree add`. NOTE the local review branch used is **`pr-<n>-review` (no `archon/` prefix)** at 1167/1185/1217, while `generateBranchName` advertises `archon/pr-<n>-review` (603) as the returned env `branchName` — an observable naming asymmetry between the recorded env branch and the on-disk branch for fork PRs.
- **New-branch creation** `createNewBranch` (1269-1340): `git -C <repo> worktree add --no-track <path> -b <branch> <startPoint>`; start-point = `taskBranch.fromBranch ?? remote/<baseBranch>` (1281-1284); "already exists" → for task `--from` case throw (1314-1321), otherwise reset `git branch -f <branch> <startPoint>` then re-add (1330-1334). `--no-track` keeps `gh pr view` from misresolving (1287-1288).
- `createFromExistingBranch` (1249-1264): plain `worktree add <path> <branch>` (no fetch/reset).
- **`copyConfiguredFiles`** (997-1052): only `worktreeConfig.copyFiles` (dedup via `Set`, 1025); the docstring at 985-995 states the **implicit unconditional `.archon` copy was removed** (superseded by `@archon/workflows` workflow-source capture); config-load failure returns `configLoadFailed: true` (warning, not failure — 1003-1022). Files copied through `copyWorktreeFiles` (worktree-copy.ts:157-179).
- **gitIdentity** `applyGitIdentity` (842-859): `git -C <worktree> config user.email`/`user.name` (non-fatal). **Submodules**: `initSubmodules` (1352-1379) default ON unless `worktreeConfig.initSubmodules === false` (817-819); `.gitmodules` ENOENT skips cheaply, other failures throw.
- **destroy** (228-339): envId is the path. If path missing → counts removed/clean already (240-244). Anchors: `canonicalRepoPath` option → `getGitCommandAnchors(...).durable`, else derive from worktree (248-261). `git worktree remove [--force]` (264-281); residual dir removed via `rm(recursive, force)` (284-300); `git worktree prune` (303-310); post-removal verification `isWorktreeRegistered` via porcelain list (313-321, 359-377); branch delete `deleteBranchTracked` = `git branch -D` (383-413, "checked out at" → warning+false); remote delete `deleteRemoteBranchTracked` = `git push <remote> --delete <branch>` (419-448).
- `get` (460-495), `list` (500-517: filters out main checkout, returns `{adopted:false}` metadata), `adopt` (529-571: "not a git repository" → null; not registered → null), `healthCheck` (581-583). Const `GIT_OPERATION_TIMEOUT_MS = 5*60*1000` (89).

### 1.5 Backend router (folder projects only)

`resolveFolderBackend` (backend-router.ts:50-86) is "the single seam where folder-project isolation is chosen" (1-12). Calling it for a non-folder codebase **throws** (62-68). ### 1.8 Worktree-copy utility

### 1.9 Errors, pr-state

- `errors.ts`: `IsolationBlockedError extends Error` with `readonly reason: IsolationBlockReason` (9-17) — signals "ALL message handling should stop" (4-8). `ERROR_PATTERNS` table (27-155) mapping lowercase message+stderr substrings → user text + `known` flag: Docker daemon messages (checked first, 31-64), `permission denied`/`eacces`, `timeout`, `no space left`/`enospc`, `not a git repository`, `cannot extract owner/repo` (**known:false** — crash), `branch not found`, `no base branch configured`, `cannot detect default branch`, `belongs to a different clone`, `cannot verify worktree ownership`, `cannot adopt`, `submodule initialization failed`. `classifyIsolationError` (160-171) returns matched message or `**Error:** Could not create isolated workspace (<msg>).` `isKnownIsolationError` (180-185): true only for `known` patterns (drives blocked-vs-crash).
- `pr-state.ts`: `PrState = 'MERGED' | 'CLOSED' | 'OPEN' | 'NONE'` (19). `getPrState(branch, repoPath, cache?, remote='origin')` (31-93): used by cleanup to catch squash-merged/closed PRs "that git ancestry checks miss" (3-6); runs `git remote get-url` (only GitHub remotes proceed — `github.com` substring check at 58), then `gh pr list --head <branch> --state all --json state --limit 1` (69-71) with 15s timeout, `cwd: repoPath`. `gh` is a soft dependency — missing/ENOENT → 'NONE' (79-89). ## 5. Pure-library notes (import-time side effects)

- **`@archon/git` — pure library.** No module-level env reads or disk I/O; all `process.env`/disk access is inside functions invoked at call time (`resolveBashPath` reads env/fs, `forge.matchSelfHostedForge` reads env). Module state is only lazy logger vars. Caveat: it imports `createLogger` from `@archon/paths`, so its import chain eventually loads `@archon/paths/logger`, whose **module top-level runs `rootLogger = buildLogger()`** (logger.ts:93) and therefore reads `process.env.LOG_LEVEL` (logger.ts:36-37) and checks `process.stdout.isTTY` (65) once. That env read is inherited, not owned.
- **`@archon/isolation` — pure library.** Imports of `index.ts` create nothing: loggers are lazy (`cachedLog` + `getLog()`), with two exceptions that build a Pino child eagerly at module load — `backends/container.ts:43` (`createLogger('isolation.container')`) and `container/overlay.ts:45` (`createLogger('isolation.overlay')`) — plus `errors.ts`/`pr-state.ts`/etc. use the lazy pattern. No env reads, no disk writes at import (the only module-level variables are `factory.ts:11-12` provider/loader slots). Instantiation needs wiring: `configureIsolation(loader)` before `getIsolationProvider()` for full functionality (factory.ts:14-22); `new IsolationResolver({ store, provider, cleanup?, staleThresholdDays? })` (resolver.ts:76).
- **`@archon/paths` — mostly pure functions, with two initialization requirements.** (1) The `logger.ts` module builds the root Pino logger at import (env read above). (2) `strip-cwd-env-boot.ts` is the deliberate side-effect entry: importing it reads the four CWD `.env` files from disk and **mutates `process.env`** — it must be the first import in CLI entry points (strip-cwd-env-boot.ts:1-13). Everything else (`archon-paths`, `env-loader`, `effort`, `install-manifest`, `detached-install-context`, `update-check`, `tier-notice`, `bundled-build`) is call-time; `update-check.ts:6` and `tier-notice.ts:16` only build child loggers at import. If you import `@archon/paths` purely for constants (e.g. `bundled-build`), you still pay the logger import unless you import from the deep module path. No telemetry capture or DB touch happens on import.
